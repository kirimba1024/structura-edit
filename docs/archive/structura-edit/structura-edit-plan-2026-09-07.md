# Structura Edit: архитектура и план первого выпуска

Исторический аудит до первого прототипа. Актуальный статус и согласованный
план находятся в [плане реализации](../../structura-edit-roadmap.md).
Указанные ниже версии, ограничения объёма и замеры относятся к первоначальному исследованию.

Статус на момент исследования: предложение, реализация редактора не начата.
Проверено 7 сентября 2026 года. Учтено последнее уточнение: поддерживаемое
решение и небольшой объём собственного кода важнее обязательного GitHub Pages;
десктоп — основная платформа. Код пишем без комментариев; объяснения храним
в документации. Текущие библиотеки в рамках этой работы не изменялись.

## Рекомендация

Первую версию делать как независимую Python-библиотеку редактирования
с необязательным десктопным интерфейсом **PySide6 + PyVistaQt/PyVista**.
Это предварительный выбор по совместимости имеющегося кода и стоимости
поддержки; качество интерактивного окна нужно подтвердить коротким прототипом.

Браузер + Three.js — нормальная архитектура. Pyodide также является
поддерживаемым способом запуска Python. Однако для нашего конкретного стека
автономный Pages сейчас добавляет собственные сборки бинарных зависимостей,
согласование их версий и второй стек интерфейса. Готового проверенного
набора WASM-пакетов у нас нет. Это инженерная работа по переносу, а не
основание считать весь браузерный подход плохим.

При последнем приоритете пользователя эти затраты не стоит включать
в критический путь первой версии. Не разрабатывать одновременно два GUI
и не переписывать Minecraft-рендер ради веба. Pages можно использовать для
документации и демонстрации результатов; автономный редактор на Pages остаётся
отдельной возможностью с критериями допуска ниже. Он не считается выполненным
локальным Python-сервером или статическим просмотрщиком GLB.

## Основания в текущем коде

Проверенные версии: core **0.5.0**, commit
`5eac3d0be7921dd319d0c0a58e8f8ba6abea8287`; render **0.7.0**, commit
`d58c5d1e11c6d5bb0a833a86d48e0273124078d2`.
Вложенные рабочие деревья на момент проверки чистые. Старые отчёты про 0.4/0.6
не использовались как описание текущего состояния.

| Найдено | Следствие для edit |
|---|---|
| `core/formats.py`: нативные NBT, Litematic, Sponge | Повторный парсер этих форматов не нужен |
| `core/nbt.py`: состояния, блоки, сущности, дополнительные NBT-поля, несколько палитр | Сохранять исходную семантику документа; массив ID блоков не заменяет документ |
| `Litematic.to_structure()` и `Schematic.to_structure()` возвращают отдельное представление | Его изменение не обновляет нативный документ; `document.save()` не сохранит эти изменения автоматически |
| Нативный `save()` сохраняет документ, экспорт в другой формат имеет описанные потери | Нужен явный путь записи изменений в исходный формат |
| `render/geometry.py`: `TexturedMesh` с массивами и `to_pyvista()` | Существующая геометрия непосредственно подходит для PyVista-окна |
| `render/mesh.py`: плотный `state` на весь bounding box, многочисленные маски и новый Atlas при сборке | Полная пересборка и память зависят от объёма, палитры, поверхностей и сущностей |
| В `TexturedMesh` нет владельца грани, номера блока или сущности | Точный выбор по геометрии нельзя получить простым чтением ID грани |
| Низкоуровневые mesh-функции отсутствуют в корневом `__all__` | Единственный адаптер, фиксация версии и интеграционные проверки; стабильность такого API не считать гарантированной |
| `RenderWarning`, `ConversionWarning`, строгие режимы и диапазоны проекций уже есть | Использовать их, а не создавать параллельные механизмы диагностики |

## Сравнение вариантов

| Вариант | Повторное использование | Дополнительная поддержка | Вывод |
|---|---|---|---|
| Python + PySide6 + PyVistaQt | Core, render и готовое преобразование в PyVista | GUI, камера, процесс вычислений, сборки для ОС | Предпочтителен для первого выпуска |
| Pages + Three.js + Pyodide | Python-логика при успешном переносе | WASM-сборки, JS-интерфейс, обмен массивами, браузерные файлы и восстановление Worker | Отдельный перенос после проверки зависимостей |
| Браузер + локальный Python | Core/render без WASM | Веб-интерфейс и локальный сервис | Технически допустим, но требует локального запуска и не решает автономный Pages |
| Полностью JS/TS | Готовые веб-компоненты | Перенос правил документов/редактирования или иной форматный стек; интеграция с Python | Не соответствует минимальному новому коду для имеющихся библиотек |

`QtInteractor` — штатный способ встроить PyVista в Qt. Это убирает необходимость
писать графический backend. Размер установленного Qt/VTK при этом может быть
существенным: компактный наш код не означает маленький установщик.
[PyVistaQt](https://qt.pyvista.org/usage.html),
[распространение Qt for Python](https://doc.qt.io/qtforpython-6/deployment/index.html).

Обёртки вроде pywebview также существуют, но не дают бесплатного совмещения
всех целей: остаются Python, веб-интерфейс и отдельная упаковка приложения.
Их не нужно добавлять третьим интерфейсом.
[Архитектура pywebview](https://pywebview.flowrl.com/guide/architecture.html).

## Что конкретно мешает простому запуску на Pages

`amulet-nbt 2.1.8` — Cython-пакет; установленная метаинформация требует
`numpy~=1.17`, то есть NumPy < 2, и `amulet-mutf8~=1.0`.
С учётом core нужен NumPy >= 1.26 и < 2. Обычные native wheels
не подходят для WASM. В проверенном официальном наборе Pyodide Amulet-пакетов нет.
[Amulet-NBT](https://pypi.org/project/amulet-nbt/),
[загрузка Python-пакетов в Pyodide](https://pyodide.org/en/stable/usage/loading-packages.html).

| Проверенный набор Pyodide | NumPy | Pillow | SciPy | Несовпадение с текущими требованиями |
|---|---:|---:|---:|---|
| 0.26.4 | 1.26.4 | 10.2.0 | 1.12.0 | Render требует Pillow >= 11; core требует SciPy >= 1.13 |
| 0.28.2 | 2.2.5 | 11.3.0 | 1.14.1 | Amulet-NBT объявляет NumPy < 2 |

Текущий проверенный stable-набор 314.0.6 содержит NumPy 2.4.6 и Pillow 12.2.0,
что также не совпадает с объявленными ограничениями Amulet/render.
Это проверка метаданных, а не доказательство невозможности портирования.
[0.26.4](https://pyodide.org/en/0.26.4/usage/packages-in-pyodide.html),
[0.28.2](https://pyodide.org/en/0.28.2/usage/packages-in-pyodide.html),
[проверенный stable-набор](https://pyodide.org/en/stable/usage/packages-in-pyodide.html).

Корректный веб-путь: воспроизводимые сборки Amulet и согласованный набор
зависимостей с проверками native/WASM. Не подменять NumPy, NBT-классы или
метаданные заглушками; не обходить ограничения зависимостей без доказанной
совместимости. Возможный перенос Amulet на NumPy 2 требует проверки
исходников, сборки и тестов; он здесь не выполнен.

Для возврата к Pages нужны четыре результата:

1. Чистая CI-сборка согласованного набора WASM wheels без ручного редактирования
   установленных файлов; зафиксированные версии и хеши.
2. В Chromium, Firefox и реальном Safari проходит цикл NBT/Sponge → изменение
   → сохранение → повторное чтение. Node и Playwright WebKit не заменяют Safari.
3. Существующий render строит текстурную геометрию без PyVista/VTK/OpenUSD;
   Three.js принимает массивы напрямую, GLB не пересоздаётся после каждого действия.
4. Измерены холодная загрузка, память, обновление, сбой/отмена Worker и реальный
   деплой по project subpath на Pages. Пустая вкладка после ожидания — не приемлемый старт.

Обычный Worker не требует SharedArrayBuffer. Однако штатный механизм прерывания
Python в Pyodide его использует и требует заголовков изоляции. Поэтому нельзя
по умолчанию обещать такой механизм на Pages. Резервный путь — завершить Worker
и восстановить последнюю подтверждённую ревизию из исходного документа и
готовых изменений, не выполняя пользовательский скрипт повторно.
[Прерывания Pyodide](https://pyodide.org/en/stable/usage/keyboard-interrupts.html),
[Worker.terminate](https://developer.mozilla.org/en-US/docs/Web/API/Worker/terminate).

## Измерения существующего render

Это native CPU-пробы на macOS ARM64, Python 3.9.6, NumPy 1.26.4 и исходниках
выше. Каждая схема запускается в отдельном процессе; три сборки с одним
AssetContext, приведена медиана двух повторных сборок. Кэш ОС не очищался.
Время включает `voxel_state` + `build_textured_geometry`, исключает создание
исходного документа, GUI, GPU, сохранение и распаковку JAR. RSS — максимум
всего процесса, включая импорты и исходный документ. Это не FPS и не веб-бенчмарк.

| Схема | Записей ячеек | Объём bounding box | Повторная сборка | Пиковый RSS |
|---|---:|---:|---:|---:|
| Встроенный дом | 427 | 1 950 | 14,1 мс | 46,1 МиБ |
| Сплошной каменный куб 64³ | 262 144 | 262 144 | 23,5 мс | 86,6 МиБ |
| Куб 64³ из шести материалов, включая стекло | 262 144 | 262 144 | 45,9 мс | 157,8 МиБ |
| Два блока на противоположных концах 512×16×512 | 2 | 4 194 304 | 53,4 мс | 118,2 МиБ |
| `[DaveGR]FantasyMedieval` | 4 385 | 29 376 | 102,9 мс | 52,0 МиБ |
| `[Arolas]MountianCastle` | 87 575 | 201 348 | 560,8 мс | 153,7 МиБ |

Для двух блоков в 1024×16×1024 срабатывает действующий лимит объёма
16 000 000 ячеек. У замка 166 записей палитры, у дома FantasyMedieval — 89.
Тесты не устанавливают универсальную зависимость времени только от палитры:
важны также модели, NBT и открытые поверхности. Реальные входы не изменялись.

Следствие: быстрый сплошной куб не доказывает быстрый редактор.
Рендерер многократно обходит объём для состояний и масок; соответствующая часть
работы имеет характер O(P·V), где P — число обрабатываемых состояний, V — объём.
Число выходных граней и сущности добавляют свою стоимость. Перенос интерфейса
в Qt не устраняет эти расходы.

Полные числа, хеши входов, методика и зависимости:
[машинный отчёт](structura-edit-plan-2026-09-07.evidence.json).

## Первый полезный сценарий

**Открыть чужую схему → осмотреть снаружи и по слоям → выбрать область или
материал → увидеть будущие изменения → применить → отменить → сохранить.**
Этот же результат должен получаться через короткий Python-рецепт.

WorldEdit уже имеет маски, кисти, паттерны и развитый clipboard. Эти операции
не являются новым преимуществом сами по себе. Наша проверяемая продуктовая
гипотеза — удобная подготовка отдельных схем вне игры с видимым результатом
Python-обработки и сохранением данных.
[Маски WorldEdit](https://worldedit.enginehub.org/en/latest/usage/general/masks/),
[паттерны](https://worldedit.enginehub.org/en/latest/usage/general/patterns/).

Минимальный первый публичный выпуск:

- Полный цикл чтения, редактирования и сохранения Structure NBT и Sponge v2/v3.
- Просмотр Litematic по выбранному региону; экспорт в другой формат — отдельное
  действие с существующим отчётом о потерях. Сохранение изменённого Litematic
  в исходный документ — следующий этап с отдельными проверками регионов и ticks.
- Orbit, свободный полёт, фокус на выделении, ортографические виды и слой Y.
- Выделение прямоугольной области и отбор по точному blockstate либо ID блока.
- Установка состояния, заполнение области, замена, удаление в явный воздух.
- Undo/redo, показ изменённых блоков и количества замен до применения.
- Выполнение Python-рецепта через тот же движок, отмена одной операцией.
- Поиск по палитре, координаты, свойства состояния, диагностика ресурсов.

Первый технический прототип поддерживает только NBT. Это средство проверить
путь целиком, а не основание объявлять остальные форматы редактируемыми.
Функции редактирования пользователь уточнит позже; список выше — проверяемая
основа, не финальный каталог команд.

Кисти сложных форм, повороты/зеркала, автоматическое соединение блоков,
симуляция жидкостей и redstone, совместное редактирование, система плагинов,
визуальный язык программирования и запись миров не входят в первый выпуск.

## Модель данных и операции

Логика редактирования не зависит от Qt, JS или событий мыши. Достаточно
`Document`, `Selection`, `ChangeSet`, `EditSession` и адаптера preview.
Это роли небольших типов, не требование создавать отдельный framework
или модуль на каждую операцию.

`Document` хранит исходный нативный документ, рабочее представление, формат,
DataVersion, регион и его origin. Позиции — целочисленные координаты документа;
координаты камеры и центрирование не меняют данные. Состояния — namespaced ID
и свойства, а не глобальные числовые Minecraft IDs. Индексы палитр локальны.

`ChangeSet` содержит первую старую и последнюю новую запись для затронутой
позиции, изменения NBT и ревизию исходного документа. Повторная запись в ту же
ячейку схлопывается; возврат к исходному значению исключается из изменения.
Полные копии документа в каждой записи undo не нужны. Бюджет истории
ограничивается байтами, а не только количеством команд.

Последовательность операции: построить изменение → проверить → показать
предпросмотр → атомарно применить → повысить ревизию → уведомить UI/preview.
Ошибка или отмена до применения оставляет документ и историю в прежнем состоянии.
Redo применяет готовый результат; скрипт с random или внешним вводом не запускается заново.

Для замены сначала проверяем состояния палитры, затем выбранные размещённые
ячейки: ориентир O(P+B_selected). Заполнение отсутствующих ячеек требует обхода
выбранного объёма, O(V_selected); его размер проверяется до выделения памяти.
Не создавать массив на всё пространство между разнесёнными регионами ради
выделения или подсчёта. Плотные NumPy-маски допускаются только для ограниченной области.

Обязательные различия: отсутствующая ячейка, явный воздух, `structure_void`,
видимость в интерфейсе и удаление. Скрытие слоя не меняет документ.
Фильтр по материалу не должен случайно объединять разные blockstate в один.

Замена типа блока очищает несовместимый block-entity payload, а undo возвращает
его полностью. При изменении свойств того же типа сохранение NBT определяется
операцией. Поля нескольких палитр, дополнительные записи и нетронутые сущности
сохраняются; политика работы с альтернативными палитрами явна.

Синтаксический `core.parse_state()` не доказывает допустимость состояния в игре.
Новые vanilla-состояния следует проверять по версионным данным существующего
проекта, например `minecraft-data`, после проверки покрытия нужной версии.
Перенос `facing`, `half`, `shape` между типами — отдельное проверенное правило,
не безусловное копирование словаря. Неизвестные исходные состояния сохраняем;
не придумываем для них defaults. Полный Java-registry не выводится из моделей JAR.
[minecraft-data и Python-обёртки](https://github.com/PrismarineJS/minecraft-data).

В NBT используем существующие валидатор и сериализатор. Для Sponge нужен тонкий
форматный адаптер, который меняет только блоковые данные и затронутые payloads
в сохранённом документе v2/v3, сохраняя биомы, offset и неизвестные поля.
Повторный NBT-парсер не нужен. Если для этого требуется публичный primitive
кодека в core, его следует отдельно выделить и проверить, а не копировать
реализацию private-функции в edit.

## Геометрия и скорость без копии render

В `preview.py` изолировать обращения к существующим `voxel_state`,
`build_textured_geometry` и flat-геометрии. Использовать один AssetContext/TextureBank
на выбранный набор ресурсов; не вызывать `render_hero()` и не открывать
новый Plotter после каждого действия. Окно и камера живут дольше геометрии.

Первый прототип может пересобирать небольшую схему полностью вне GUI-потока.
Это проверка интеграции. Для заявленного быстрого редактирования замка такой
режим недостаточен: измеренная задержка одной сборки около половины секунды.

Планируемое обновление по частям:

1. Участки с устойчивыми координатами; размер 16³ или 32³ выбрать по измерениям.
2. Изменение помечает затронутый участок и зависимости соседей. Контекст соседей
   нужен для culling, жидкостей и соединений; радиус не объявлять универсальным
   для любых будущих моделей.
3. Сборщик читает соседний контекст, но выдаёт геометрию только принадлежащих
   участку объектов. Сущность на границе выводится один раз с постоянным ID.
4. Новые буферы заменяют только соответствующие части сцены; старые GPU-ресурсы
   освобождаются. Камера и выделение остаются на месте.
5. Результат принимается только при совпадении ревизии документа и ресурсов.
   Очередь объединяет устаревшие запросы; не растёт на каждый mousemove.

Сегодня этого контракта в render нет. Также нет ID владельца грани.
Он нужен для точного picking сложных блоков и сущностей. Получение позиции через
`floor(hit - epsilon * normal)` не годится как общий алгоритм для повёрнутых,
выступающих или декоративных моделей. Обрезка chunk-геометрии по центрам
треугольников также не решает корректно границы и владение.

При текущем запрете на изменения render можно проверить окно, пространственные
выделения коробкой, 2D-слои и пакетные операции. Перед выпуском полноценного
точного 3D-инструмента нужен отдельно согласованный минимальный контракт:
владелец грани/объекта, вход с соседним контекстом, границы выдаваемых объектов.
Эта работа не выполняется скрыто в edit через monkey patch или копию mesh.py.

Атлас сейчас строится заново и выдаёт общие UV. Простая замена одного блока
может затронуть раскладку. Сначала допустим атлас на участок с повторным
использованием одинаковых материалов; измеряем число материалов и дублирование
текстур. Общий изменяемый глобальный атлас, greedy meshing и GPU-instancing
не добавлять заранее: они усложняют UV, прозрачность и связь с picking.

## Python, GUI и восстановление

Геометрию и длинные Python-операции выполнять в рабочем процессе через
стандартный multiprocessing с режимом spawn; Qt/VTK-объекты остаются в GUI.
Один QThread сам по себе не гарантирует отзывчивость CPU-heavy Python из-за GIL.
Процесс получает операции и ограниченные данные, возвращает ChangeSet/массивы;
сетевой сервер для этого не требуется. IPC и очереди ограничиваются по размеру.

UI и Python API используют одну историю. Qt actions вызывают EditSession;
не создавать независимый QUndoStack, расходящийся с headless-операциями.
Рецепт в UI получает рабочую копию выбранных данных и формирует одно изменение.
Встроенный запуск — явное действие; открытие схемы или проекта код не выполняет.

Результат с устаревшей base_revision отклоняется. При остановке процесса
восстанавливаются последняя подтверждённая ревизия и готовые изменения.
Запись файла атомарна. Сохранение в другой формат использует существующие
предупреждения о потерях; исходный файл не подменяется неожиданно.

Не обещать неблокирующий `show()` в любом Python-скрипте: Qt требует работающий
event loop. CLI владеет QApplication; интеграция с IPython/существующим Qt
приложением — отдельный документированный режим. Первый live-сценарий —
рецепт из UI с немедленным preview, а headless API остаётся обычным Python.
[Ограничение BackgroundPlotter](https://qt.pyvista.org/usage.html).

Пример формы будущего API, не существующий интерфейс:

```python
from structura_edit import EditSession

session = EditSession.open("house.nbt")
selection = session.select(bounds=((0, 0, 0), (16, 32, 16)))
change = session.replace(selection, source="minecraft:oak_planks", target="minecraft:spruce_planks")
session.apply(change)
session.undo()
session.redo()
session.save("house-edited.nbt")
```

Границы selection полуоткрытые. `replace` выше строит изменение; `apply`
совершает его. UI предпросматривает тот же ChangeSet. Конкретные имена
закрепляются после первого сценария, без дополнительных DSL и plugin API.

## Интерфейс и визуальное качество

Один рабочий экран на стандартных Qt widgets и QtInteractor:

| Зона | Содержание |
|---|---|
| Верхняя узкая панель | Файл, сохранение, undo/redo, режим просмотра, состояние документа |
| Слева, сворачивается | Регионы и поиск по палитре с количеством блоков |
| Центр | Большая 3D-сцена, выделение, ориентир осей, минимум постоянных перекрытий |
| Справа, по контексту | Координаты, blockstate, параметры текущей операции и preview |
| Снизу | Слой Y; панель рецепта и диагностики раскрывается по запросу |

Пропорции проверить на 1366×768 и 1440×900: сцена остаётся главным содержимым.
Одна согласованная тема, системный читаемый шрифт, единая сетка отступов,
небольшой набор иконок с подписями/подсказками. Не писать собственные кнопки,
докинг, файловые диалоги или механизм масштабирования интерфейса.

Выделение, будущие изменения и применённые изменения визуально различимы.
Числа и подписи дополняют цвет. Текстуры показываются с правильной фильтрацией;
стекло, листва, вода, таблички и сущности проверяются по эталонным сценам.
Не скрывать отсутствующие модели без объяснения и не выдавать статические
сущности render за полноценную анимацию Minecraft.

Свободный полёт: явное включение, WASD, вертикальное перемещение, регулируемая
скорость, Esc для выхода. Скорость не зависит от FPS; фокус в текстовом поле
отключает навигационные клавиши. Orbit доступен сразу; режим с коллизиями
не входит в первый выпуск. Пересборка сцены не сбрасывает камеру.

Пустой старт предлагает открыть файл или встроенный пример. На desktop
используется существующее обнаружение Minecraft-ресурсов; при необходимости
пользователь выбирает JAR. Один выбор ресурса на проект, затем кэш.
Проверенный JAR 1.21.1 имеет размер 26 836 906 байт; выбранные нынешним
extractor ресурсы — 8 497 файлов, 4 807 431 байт до сжатия.
Размер JAR не равен объёму нужных ресурсов. В нём не найден `reports/blocks.json`.
Из этих чисел нельзя выводить время распаковки или размер других версий.

## Будущий участок мира

Сначала **просмотр выбранного участка Java-мира**, затем экспорт выделения
в схему. Запись обратно в мир — самостоятельная задача.

Сразу сохраняем раздельные понятия источника, региона/секции и документа
редактирования. Будущий WorldSource читает ограниченные участки, а не
превращает весь мир в одну Structure. Для секций храним origin и целочисленные
координаты; отрицательные X/Y/Z допустимы. Деление на секции использует floor,
не усечение к нулю. В GPU передаются координаты относительно близкого origin,
чтобы float32 не портил точность на больших мировых координатах.

Источник .mca должен учитывать версии Java, измерение, отсутствующие секции,
палитры, упаковку states, block entities и отдельные данные сущностей.
Биомы и освещение влияют на внешний вид; их отсутствие надо отражать в
контракте просмотра, а не имитировать точное совпадение с игрой.

Для чтения сначала оценить существующий Amulet API с закреплённой версией.
Его нормализованное представление не считать автоматически lossless Java NBT.
Для любого выбранного reader нужны независимые fixtures целевой версии.
Prismarine также имеет Anvil provider и chunk-based viewer; это подтверждает
существование готовых компонентов, но не их совместимость с нашим render.
[Amulet Level API](https://amulet-core.readthedocs.io/en/stable/api_reference/api/level/base_level/index.html),
[Anvil provider](https://github.com/PrismarineJS/prismarine-provider-anvil),
[Prismarine viewer](https://github.com/PrismarineJS/prismarine-viewer).

Большой мир требует ограничения видимой области, очереди загрузки и LRU-кэша
секций/геометрии. Общий плотный bounding box недопустим. Не создавать
сейчас универсальную систему плагинов: отдельного адаптера источника достаточно,
когда появится второй реальный источник данных.

## Порядок реализации и критерии допуска

| Этап | Конкретный результат | Проверка перед следующим этапом |
|---|---|---|
| 0. Проверка выбранного GUI | QtInteractor с текущей текстурной геометрией, orbit/free look, фоновая пересборка и стабильная камера | Запуск из установленного окружения; реальные схемы; графические артефакты и задержки измерены. Render не изменён |
| 1. Headless edit | NBT, Selection, ChangeSet, транзакции, undo/redo, сохранение | Ошибка не меняет состояние; redo повторяет результат; сохраняются NBT, воздух и палитры |
| 2. Форматная целостность | Редактирование/сохранение Sponge v2/v3, просмотр Litematic и явный экспорт | Сравнение нетронутых полей; повторное чтение; независимые fixtures; offsets и biomes сохранены |
| 3. Основной экран | Выделение, замена/заполнение, preview, слои, палитра, клавиатура | Полный пользовательский сценарий без терминала и ручного исправления файла |
| 4. Программная обработка | Рецепт → ChangeSet → preview → apply; отмена/восстановление | Ошибка и принудительная остановка не повреждают последнюю подтверждённую ревизию |
| 5. Интерактивная производительность | Минимальный согласованный контракт источников геометрии и обновлений участков | Точное picking; швы и сущности на границах; отсутствие утечки буферов. Без изменения контракта ограничить объявляемые возможности |
| 6. Выпуск | Пакет, GUI extra, готовые сборки, документация, примеры и демонстрация | Чистые Windows/macOS/Linux; обычный пользователь проходит сценарий; поддержка заявлена только для проверенного |
| После первой версии | Нативная запись Litematic, согласованные новые инструменты, затем WorldSource | Отдельные контракты для ticks/регионов, transforms и версий миров |

Этапы 0–4 выполняются на существующем render. Этап 5 обозначает внешнюю
зависимость качества, а не разрешение менять render в текущей задаче.
До появления нужного API нельзя обещать точное редактирование любых моделей
и мгновенные обновления больших построек.

Цели измерений для следующего прототипа, **не достигнутые показатели**:

- Камера на целевых сценах: стремиться к 60 FPS; p95 времени кадра до 33 мс
  на зафиксированном контрольном устройстве при 1080p.
- Малое изменение на замке: p95 от действия до готовой геометрии до 150 мс;
  одной полной пересборкой с текущими 561 мс эта цель не выполняется.
- Большая операция показывает прогресс и допускает отмену; нет роста очереди
  при повторных командах. Время операции, сериализации и GPU upload измерять раздельно.
- 100 последовательных правок/undo не дают неограниченного роста памяти;
  ресурсы ограничены документом, бюджетом истории и кэшем.

Набор проверок: плотный и разреженный объём, много состояний, стекло/листва,
двери/лестницы, NBT табличек и контейнеров, сущности за пределами ячейки,
несколько палитр, отрицательный origin, повреждённый/слишком большой файл,
смена assets, отмена и устаревший результат. Проверять семантику сохранённого
NBT, а не требовать совпадения gzip-байтов после реального редактирования.

Для независимой библиотеки базовый импорт не открывает окно и не требует Qt.
GUI-зависимости подключаются extra. Точные версии Qt/PyVistaQt фиксируются
после совместного smoke test с поддерживаемой PyVista render; не брать
несовместимые latest. Матрицу Python edit можно сузить под GUI, не меняя
поддержку Python существующих библиотек.

## Минимальный код и распространение

Ориентир организации: несколько модулей данных/операций/истории, один preview
adapter и небольшой пакет ui. Не обещать заранее число строк: корректный
round-trip и управление жизненным циклом важнее искусственного лимита.
Экономим за счёт повторного использования кодеков, Qt widgets и render,
отсутствия двух GUI, custom RPC framework, registry вручную и DSL.

Пользователь должен быстро получить полезный результат: ясный README,
короткая запись «открыть → заменить → сохранить», готовый пример и обычная
установка GUI. Для Python — отдельный короткий рецепт и типизированный API.
До публичного распространения требуется выбранная владельцем лицензия:
в проверенных деревьях core/render LICENSE не найден. Это открытый пункт
выпуска, не предложение самовольно выбрать лицензию.

Популярность нельзя гарантировать архитектурой или обещанием «лучше WorldEdit».
Проверять гипотезу на авторах построек: могут ли они без помощи выполнить
реальную замену, увидеть ошибки и сохранить пригодный для игры результат;
используют ли инструмент повторно. Собирать конкретные неудобства и только
после этого расширять команды. Рейтинг, количество будущих установок и
универсальное преимущество над существующими редакторами не установлены.

## Границы проведённой работы

Прочитан код двух библиотек и актуальные отчёты, проверены зависимости и
официальные документы, выполнены восемь native CPU-проб и чтение оглавления
реального client JAR. Созданы этот план и машинный отчёт.
WASM-пакеты не собирались; полноценный браузерный или Qt-редактор не запускался;
GPU и установка на других ОС не проверялись. Приведённые API и UI — предложения.
