# Компактные ответы worker, страницы поиска и sparse-операции

11 сентября 2026. Продолжение [worker lifecycle](worker-lifecycle-2026-09-11.md)
и пунктов 3–4 [очереди](next-priorities-2026-09-11.md). Три направления объединены
сокращением работы над неизменившимися данными. Владельцы состояния и порядок
подтверждения истории сохранены; новых процессов, очередей или общих framework нет.

## Контракт обмена

Для обычного Apply блоков и одного шага Undo/Redo без resize/сущностей worker
возвращает `DocumentDelta`: версию исходного снимка, итоговые значения затронутых
ключей overlay/patch, метаданные History и transition. Удаление ключа выражено явно.
Все NBT-значения клеток сохраняются. Новый token остаётся во внешнем TaskSuccess.

Поток `worker-exchange` проверяет исходную версию и идентичность Document, копирует
изменяемые словари и собирает самостоятельный EditSession. Он не выполняет Apply/Undo
повторно, не пишет SQLite, не генерирует новые revision/state ID. Callback GUI
получает привычную сессию. Нет изменений ViewPipeline/EditorDocument для поддержки
второго вида результата. Сборка в потоке обмена сохраняет его существующий lifecycle:
Cancel ждёт завершения одного потока, старый результат не публикуется, ошибки
очищают подтверждённый снимок; повтор команды автоматически не выполняется.

Очистка старой redo-ветки по-прежнему ждёт следующего запроса с подтверждённым
снимком. Потеря ответа или сбой его восстановления оставляют GUI прежнее состояние
и рабочую redo-ветку. Отдельно проверен явный повтор с новым исходным снимком.

Полный ответ сохраняется для Save, resize, изменений сущностей, перехода через
несколько записей истории и пользовательских подклассов сессии. Это явная граница
оптимизации: компактный формат не пытается описать любое изменение объекта.
Копирование словарей при восстановлении всё ещё O(P), метаданные истории O(H).
Новый модуль worker_delta содержит только этот контракт и его сборку; persistent
maps, журнал для синхронизации процессов и дополнительные слои не вводились.

## Object Search

Один последний запрос хранит bool-маску и накопленные счётчики по 4096 строк.
Новая страница находит нужный участок по счётчикам и извлекает не больше одного
небольшого чанка индексов за раз. Новый запрос освобождает предыдущую маску.
CellSet фильтруется такими же порциями, без Python-списка всех совпадений.

Бюджет 64 MiB общий для индексов блоков и сущностей, маски, счётчиков и консервативного
резерва рабочих массивов/строк. Collect проверяет и число объектов, и память будущих
строк до их создания. Это бюджет данных поиска, не лимит RSS или памяти исходного
NBT. Исходная структура и Python allocator могут занимать дополнительную память.

ObjectFinder использует отдельную типизированную команду в существующем слоте
WorkerDocument: Next больше не вызывает session.fork и не передаёт всю сессию.
Каждый новый снимок явно сбрасывает индекс, включая одинаковые revision после
Reload. Проверки task ID и generation UI сохранены. Порядок прежний: сущности перед
блоками, стабильность внутри одного индекса; глобальная сортировка не добавлялась.

На готовом индексе из 3 млн блоков, все совпадают с `minecraft:`: первая маска
заняла 3,85 мс; прежняя страница с материализацией всех совпадений — 3,44 мс;
страница сохранённого запроса — 0,083 мс. Peak дополнительных аллокаций tracemalloc:
27 000 593 → 3 050 348 байт на первый запрос и 27 241 байт на повторную страницу.
Сохранённая маска и счётчики: 3 005 872 байта. Первая страница не обязательно быстрее.

Отдельно реальные worker-запросы для 100k блоков: построение индекса API 50,06 мс,
первый холодный worker-запрос 201 мс, `minecraft:` → Next → Next → Next:
3,29 / 1,61 / 1,59 / 1,62 мс. Размер тела команды страницы — 136 байт без конверта token/task ID.

## Разреженные операции

`stored_positions(selection)` выбирает меньший обход между самим выделением
и присутствующими позициями базы/overlay. Явно записанный воздух остаётся записью;
отсутствующие позиции не превращаются в новые клетки. Общий метод применяется
в Replace по материалу, Copy, palette counts и сборе столбцов Top/Overlay surface.
Условия Condition и общий перебор фигур сохраняют свои прежние бюджеты и семантику.

Copy проверяет читаемость мира до обхода и ограничивает число сохранённых объектов.
Footprint разреженного CellSet сохраняет отверстия. Paste/Stack без Air считают
реальные блоки и сущности; с Air учитывают всю область/footprint. Проверки конечного
ChangeSet, загруженных чанков, resize и объёма будущего preview не ослаблялись.

Пять измерений API: Replace 10 клеток среди 500k исходных записей — 132,28 → 0,037 мс.
Copy двух блоков в области 1 млн клеток — 154,69 → 0,015 мс. Для старого Copy измерен
его перебор без прежнего раннего отказа по объёму; новая операция проходит при
operation_limit=10, включая Paste без Air. Это не изменение цены плотного Fill.
