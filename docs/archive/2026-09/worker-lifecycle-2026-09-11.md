# Worker: версии запросов и один снимок документа

11 сентября 2026. Реализован ограниченный этап из
[очереди](next-priorities-2026-09-11.md): явный lifecycle и хранение одного снимка
для команд EditWorkflow. Транспорт остаётся прежним — один процесс, Pipe и поток
обмена. Параллельных операций над документом и автоматических повторов нет.

## Контракт

| Граница | Правило |
|---|---|
| Запуск | У каждого запроса новый task ID; STARTED означает отправленный на выполнение запрос, BUSY — отказ из-за занятого runner, FAILED_TO_START — ошибку отправки/запуска |
| Progress и результат | Принимаются только для текущего task ID; success и failure — разные типы сообщений |
| Cancel | ID и callback инвалидируются, процесс завершается; до выхода прежнего потока обмена сохраняется CANCELLING |
| Новая задача | Разрешена после завершения предыдущей; повторные Cancel не создают дополнительные потоки |
| Сбой процесса | GUI сохраняет свой снимок; команда не повторяется автоматически; следующий явный запрос заново передаёт документ |
| Callback | Состояние завершённой задачи освобождается до callback; следующая задача не теряется, даже если предыдущий callback затем выбрасывает исключение |
| Защищённые операции | Apply, History, Save и прежние защищённые задачи нельзя отменить через runner; ошибка отображения started не обрывает уже начатую запись |

Состояния runner: IDLE → STARTING → RUNNING → IDLE/FAILED; отмена проходит через
CANCELLING. Пока поток подготовки выходит, GUI показывает `Stopping task…`.
Python-поток с произвольной зависшей функцией нельзя безопасно убить. В таком случае
новые задачи остаются заблокированы до его выхода или перезапуска приложения;
новые потоки вместо зависшего не создаются.

Task ID, версия данных и актуальность пользовательского ввода решают разные задачи.
`DocumentToken` содержит snapshot ID, document ID, revision и state ID. Новый объект
сессии или базового Document требует нового снимка, даже с прежней revision после
Reload. Прежние input/session tokens EditorDocument дополнительно отбрасывают preview
после изменения ввода, выделения и повторного открытия. Параметры operation и
размещения захватываются при создании команды; описание preview читает те же значения.

## Владение и история

Worker удерживает один документ. Первый запрос EditWorkflow передаёт снимок,
последующие при совпадающем token — только команду. Подготовка operation, recipe,
repeat, placement plan, paint и NBT batch возвращает результат операции. Apply,
History и Save выполняются над сохранённым документом и возвращают полный новый
снимок с новой версией; GUI публикует его через прежний EditorDocument.replace.
Обычный EditWorkflow сохраняет bool-результат запуска, явный SubmitResult относится
к TaskRunner.

Ошибка выполнения сбрасывает сохранённый документ. Open, World, Recover и загрузка
области размещения также сбрасывают снимок и индекс; это свойство задаётся в
существующем TASKS. Рендер и прочие вспомогательные задачи используют типизированную
оболочку транспорта, но их параметры пока остаются прежними TaskCall.

SQLite-history создаётся родительским процессом и переживает отмену worker.
Особый случай — Apply после Undo: worker мог записать новую ветку, а ответ мог
потеряться. Поэтому удаление старых redo-строк откладывается до следующей команды
с подтверждённым снимком. Без ответа старая GUI-сессия сохраняет рабочий Redo.
Обычный Python API продолжает удалять недостижимые строки в транзакции Append.
При потере ответа новая недостижимая строка может остаться до удаления временного
журнала; это допустимый расход диска при сбое, а не повреждение доступной истории.

Сбой после записи внешнего файла не доказывает, что файл не изменился. GUI остаётся
dirty, автоматического повторного Save нет. Тесты отдельно моделируют частичный
переход истории, потерю ответа Apply и ошибку после записи файла.

## Замеры Pipe

`benchmark_worker_document.py`, пять повторов, настоящий spawn/Pipe и SQLite.
Один загруженный блок; остальной world patch синтетический и вне окна. Медианы в мс,
`до` — полная передача сессии на том же коде, `после` — повторное использование
подтверждённого снимка. Размер сообщений измеряется отдельно от времени.

| Накоплено | Подготовка правки до → после | Apply до → после | Undo до → после | Redo до → после |
|---:|---:|---:|---:|---:|
| 0 | 5,96 → 4,43 | 8,87 → 6,29 | 6,45 → 4,82 | 6,25 → 4,77 |
| 100k | 96,77 → 3,25 | 45,74 → 25,00 | 44,93 → 24,25 | 44,90 → 23,73 |
| 300k | 291,43 → 3,26 | 137,68 → 71,88 | 136,08 → 70,64 | 136,88 → 69,68 |
| 500k | 513,16 → 3,32 | 268,37 → 141,32 | 266,48 → 133,12 | 270,65 → 132,33 |

При 500k тёплый запрос подготовки уменьшился с 7 873 282 до 544 байт, Apply —
с 7 873 808 до 911 байт. Ответ Apply всё ещё занимает 7 873 453 байта.
Общие immutable клетки в fixture уменьшают pickle: это не оценка размера
произвольного мира с большим NBT. RSS после сценария: родитель 318 → 326 MiB,
worker 181 → 175 MiB; это текущие значения, не измерение максимальной памяти.

## Сквозной GUI

Одинаковая постройка в 24 этажа: 28 800 исходных блоков, 57 625 изменений, NBT,
сущности и расширение с отрицательным offset. Native Qt, видимое окно 1104×720,
viewport 1104×660. Один контрольный прогон `--full-session` и два новых, без
профилирования и трассировки, последовательно.

| Этап | Полная передача, мс | Новый путь, два прогона, мс |
|---|---:|---:|
| Preview | 2718,75 | 2863,15 / 2862,46 |
| Apply | 2170,38 | 2060,05 / 2067,90 |
| Save | 1210,40 | 900,10 / 907,09 |
| Undo | 1977,35 | 1298,05 / 1303,70 |
| Redo | 1703,18 | 1027,60 / 1000,99 |

Preview стал примерно на 5% дольше; устойчивого улучшения его максимальной
паузы нет: 424 мс в контроле, 233/436 мс в новых прогонах. Save ускорился примерно
на 25%, Undo на 34%, Redo на 40%. Сумма sampled peak RSS GUI+worker выросла
с 1281,80 до 1330,89/1333,91 MiB, примерно на 4%. Общие страницы могут учитываться
дважды. Это измеренный компромисс, а не обещание ускорения каждой стадии GUI.

## Проверки и следующий шаг

Проверены ошибки запуска, поздние progress/success/failure после Cancel, повторный
Cancel, отмена в prepare_args, смерть процесса, запуск задачи из callback,
исключение после такого запуска, сбои recipe/history/save, старый документ и
изменение входных значений. Три последовательности по 45 действий выполняются
через настоящий worker; после каждого шага состояние и cursor сравниваются с
независимой моделью истории.

Полный прогон: 1013 passed, 21 warnings; Ruff и diff check пройдены. Mypy 1.18.2
строго проверяет два новых модуля границы, с пропуском импортируемой реализации.
Legacy payload и значения параметров operation ещё используют Any. Это начало
проверки типов, а не доказательство полноты typing всего публичного API.

`smoke_world_edit.py` прошёл Import → другая область → Undo/Redo → Save с проверкой
backup/NBT → сохранение обратного patch. `smoke_building_workflow.py` прошёл
отмену инструментов, стену, четыре этажа, Take, Save, Undo, восстановление черновика
и повторное сохранение. Сборка `--skip-install` обновила app и ZIP; проверка подписи
и установленного приложения прошла, включая NBT batch на 70 объектах, обзор мира,
быструю смену срезов, телепорт и отмену. Файлы — в `dist/` библиотеки edit.

Защита CodeVersion сохранена. В editable workspace проверка 236 Python-файлов
заняла медианно 1,37 мс за 50 проходов. Сканирование каталогов собранного пакета
измерено отдельно и записано в evidence; оно не заменяет замер всего frozen worker.

Native GUI и сборочные результаты, полные замеры и версии сохранены в
[evidence](worker-lifecycle-2026-09-11.evidence.json). Физический ввод и другие
платформы этим этапом не проверены; личные миры не изменялись.

Следующий ограниченный шаг — типизированный ответ с delta для Apply/History
и нужные снимки секций для render. До замены полных ответов нужно сохранить
независимость опубликованных GUI-снимков и порядок подтверждения истории,
избежать повторного исполнения операции в GUI. Затем — память и пагинация
Object Search и адаптивный обход sparse-выделений. Capabilities, общий API ошибок,
CI и группировка пакетов не смешиваются с этим изменением транспорта.
