## Как определять приоритет

Сначала устранять воспроизводимое неправильное поведение. Затем сокращать путь частых действий. После этого добавлять инструмент с ясной семантикой и ограниченной областью реализации. Оптимизацию начинать с измеренного ограничения.

Не назначать декоративные баллы или сроки без данных о частоте задач и стоимости реализации. Ошибка сохранения блокирует выпуск соответствующего сценария записи; она не требует заморозить независимые улучшения редактирования схематики. Полное восстановление сессии не должно превращаться в многомесячное предварительное переписывание редактора.

## Ближайший этап: шесть пакетов работ

### R1. Правильно считать различия относительно сохранённого состояния

**Воспроизведено.** После изменения одного блока и Save: `dirty=False`, но `Unsaved changes` показывает одну правку. После Undo: `dirty=True`, на диске gold, локально stone, но счётчик показывает ноль. `changes_view` читает overlay относительно исходного документа, тогда как Save сдвигает сохранённую точку истории.

**Изменение.** Разделить три основания сравнения: до текущей операции, при открытии, после последнего успешного Save. Использовать сохранённую базу для unsaved-сводки. Для мира учитывать глобальный patch, включая данные вне загруженного окна; выделить общее количество и видимую часть. Учесть сущности и resize, не только блоки. Историю сохранить. Не брать полную копию мира ради индикатора.

**Готово:** Edit → Save → Undo → Save → Redo даёт согласованные dirty, сводку и повторно открытый файл; возврат к открытому после Save показывает обратные несохранённые правки. Отмена и неуспешный Save не перемещают сохранённую базу.

**Узлы:** `changes_view.py`, `changes_ui.py`, `session.py`, `world_view.py`, `world_changes.py`, `editor_document.py`. Это первый компактный исправляющий PR.

### R2. Довести существующее восстановление мира

**Воспроизведено два случая.** Ошибка второй замены оставляет первый файл новым, второй старым. Backup с `before_hash=null` успешно проходит Verify, но Restore падает с FileNotFoundError: файл отсутствовал до Save, поэтому его нужно удалить, а код пытается копировать отсутствующую резервную копию.

**Первая поставка:** правильно представить отсутствие файла, восстановление создания/удаления и защитную копию текущего состояния. Не добавлять новый браузер backup.

**Следующая поставка:** до установки сохранить долговечный manifest с идентификатором мира, схемой, pre/post-хешами, списком действий и фазой операции. Применять тот же протокол к восстановлению. Обновлять manifest через временный файл; определить fsync файлов и каталогов для поддерживаемой платформы. Проверять принадлежность и допустимость путей из manifest. При перезапуске сверять фактические хеши, поскольку процесс может завершиться между replace и обновлением фазы.

В первой версии достаточно проверяемого возврата к состоянию до Save; автоматическое завершение записи требует дополнительно сохранить подготовленные новые файлы. При сторонних изменениях показывать конфликт. После незавершённой установки не начинать следующую запись того же мира без разрешения состояния восстановления.

**Готово:** искусственный отказ до/после каждого replace, при записи manifest, при удалении файла и во время Restore; перезапуск; новые и исчезнувшие файлы; сторонняя правка между проверкой и установкой. Исход и возможность восстановления явно определены. Многофайловая атомарность и исключение стороннего писателя не заявляются.

**Узлы:** core `world_staging.py`, writer и его тесты; edit `restore_ui.py`, обработка открытия/ошибок. Проверки на временных мирах обязательны до расширения сценария записи оригиналов.

### R3. Ограничить удерживаемую историю

**Воспроизведено.** Сто раз вернуть cursor к началу и добавить ветку: одна достижимая запись, 100 строк SQLite и 100 элементов RAM-кэша.

**Изменение.** При удалении redo-ветки освобождать её записи и кэш после завершения возможных читателей. Проверить фактическое владение историей в worker, не строить универсальный сборщик мусора без необходимости. Учёт кэша вести по оценке удерживаемых байтов, включая NBT; сжатый размер отдельно от RAM. Не выполнять VACUUM после каждого действия. Большую сериализацию и запись оставить вне GUI.

**Готово:** многократное ветвление не наращивает недостижимые записи; большие NBT не обходят бюджет малым числом блоков; Undo/Redo после вытеснения работают; отказ SQLite оставляет документ прежним. Отдельно измерить пик сериализации.

**Узлы:** `history.py`, `session.py`, путь защищённых задач. Восстановление после перезапуска — отдельный пакет, не побочный эффект переименования временного каталога.

### R4. Завершённый Save и согласованный ввод

**Подтверждено кодом.** Закрытие предлагает Discard/Cancel. Для схематики каждый Save as предлагает новый `-edited`. Меню Undo подписано именем предыдущей операции, хотя обработчик при pending отменяет preview. В latched freelook Shift-клик передаёт `extend=True`, хотя preview расширения подавлен.

Разделить на независимые маленькие изменения:

- `Save / Save as… / Export selection…`; первый выбор рабочего пути, затем повторное сохранение туда. Демо предлагает пользовательский каталог, регистр расширения нормализуется.
- Close/Open после Save продолжаются только из успешного callback. Отмена выбора пути, конфликт и ошибка записи оставляют прежний документ открытым. Save не применяет pending-preview молча.
- Вычислять действие и подпись Undo согласованно; отдельная доступная отмена preview. Смысл Shift для hover и click выводить из одного состояния ввода.

**Готово:** три сохранения без цепочки суффиксов; успешный и неуспешный Save при Close/Open; Undo с пустой/непустой историей и preview; Shift-клик в полёте и вне полёта, в том числе при сущности перед блоком.

**Узлы:** `source_ui.py`, `menus.py`, `edit_workflow.py`, `navigation.py`, `ui.py`. Автоматический вход в полёт — отдельная UX-настройка, а не доказанная ошибка; не менять привычный default без явного решения по продукту.

### R5. Явные границы совместимости

**Воспроизведено.** Clipboard с DataVersion 3955 принимается документом 2865 без проверки совместимости. Это подтверждает отсутствие проверки, а не порчу конкретных данных.

**Изменение.** Общая проверка возможностей в API и GUI: формат × версия × чтение блоков/объектов × редактирование × экспорт × запись. Для первой реализации межверсионный перенос блокировать предметным объяснением, пока нет проверенного пути преобразования. Совпадение DataVersion — необходимая исходная проверка, а не доказательство совместимости модовых схем. Неизвестный ID не считать неверным только из-за отсутствия текстуры.

Конкретный пробел: Minecraft 26.1 перенёс `playerdata` в `players/data` и заменил `Player` ссылкой `singleplayer_uuid`; текущий `player_entities` читает старый путь и тег. Это вывод из сопоставления кода и [официального описания 26.1](https://www.minecraft.net/en-us/article/minecraft-java-edition-26-1), без запуска настоящего мира этой версии. Проверить игрока и измерения отдельными fixture; не объявлять всё чтение 26.1 сломанным.

**Готово:** поддержанные комбинации проходят семантический round trip; неподдержанные действия объяснены до расчёта; данные не «конвертируются» сменой одного DataVersion. Для новых схем сначала фикстура и проверка core, затем разрешение действия в edit.

**Узлы:** политика форматов в core, `document.py`, `source_loading.py`, `clipboard_placement.py`, `world_view.py`. Не начинать с универсального конвертера всех версий.

### R6. Одна сводка последствий операции

**Частично реализовано.** Есть preview, контур unsaved и review условного размещения. При Replace all путь размещения может сразу применить подготовленный результат; дух не показывает всех удаляемых данных.

**Изменение.** Из готового ChangeSet получать добавления/удаления/замены, изменения block-entity NBT, сущностей и bounds, а также число изменений вне видимого среза. Причины пропуска собирает планировщик: их невозможно восстановить из одних дельт, в которых пропущенных клеток нет. Детали тяжёлого NBT раскрывать по запросу.

Review доступен для любого Paste. Для удаления содержимого контейнеров и разрушительной вставки с Copy air показывать точный результат до commit; не добавлять одинаковые модальные подтверждения каждой небольшой вставке. Apply использует именно подготовленный ChangeSet и проверяет его ревизию.

Компактный постоянный статус документа отделить от сообщений о рендере и скорости. Нерешённые предупреждения доступны без Python-панели. В самой панели Python кратко назвать запуск локального кода и границы Cancel, без разработки новой песочницы.

**Готово:** воздушная полость поверх комнаты, сундук в заменяемой стене, сущности при Keep existing, скрытый этаж и ноль совпадений объяснены до Apply. Смена параметров запрещает применение старого результата. Геометрия и статистика относятся к одной операции.

**Узлы:** `ChangeSet`, планы placement/operations, `placement_review.py`, `edit_workflow.py`, панели. Сначала счётчики и переход к затронутым объектам; полноценный экран попарного сравнения можно добавить позднее.

## Следующий прирост полезности

После исправления затронутых контрактов выпускать законченные небольшие возможности. Предлагаемый порядок для работы с постройками:

| Порядок | Пакет | Минимальная поставка и критерий |
|---|---|---|
| F1 | Материалы и доступ к существующим операциям | Catalog / In build / Recent; английское имя и ID, поиск в ресурсах/реестре выбранной версии, ленивые миниатюры и сохранение recent. Replace/Fill видимы возле выделения; меню и поиск используют те же действия и причины недоступности. Новый материал выбирается без знания ID |
| F2 | Экспорт выделения в Sponge `.schem` | Общий exporter core, не один новый файловый фильтр. Состояния, NBT, сущности, размеры и anchor проверены повторным открытием, затем независимым совместимым инструментом. Явно определить, как разреженный footprint кодируется в прямоугольном формате и какие пропуски превратятся в воздух |
| F3 | Условия и пресеты смесей | AND/OR, Y range, защита block entities, различие строгих свойств и нынешнего lenient-режима. Те же правила для From/маски/назначения при сохранении их разных ролей. Пресет Mix хранит версию алгоритма и local/world anchor; после этого простой градиент по высоте |
| F4 | Planar select → Extrude → Frame | Выбор связной плоской грани; целочисленное выдавливание; затем внутренняя/наружная рамка. Положительная глубина, полные кубы без NBT и составных блоков в первой версии; неподдержанные данные явно исключены. Одна операция — один Undo |

F1 и F2 не зависят от нового движка выделения. F4 не требует заранее строить общий 3D-скульптинг или библиотеку всех расстояний. Минимальные необходимые условия из F3 можно внедрять вместе с конкретным инструментом, без отдельного языка выражений.

В F1/R4 включить небольшой проход оформления: исправить белый текст на accent, фокус, длинные значения и прокрутку панели. Текущий расчёт: белый на `#26a888` — 2.9834:1, основной текст на панели — 10.2837:1. Для обычного значимого текста взять 4.5:1 как инженерный ориентир из [W3C](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html). Сохранить тему и Monocraft; не выдавать расчёт двух цветов за полную проверку доступности. Проверить native Qt, узкое окно и Retina.

## Длительная работа и специализированные возможности

**D1. Восстановление черновика.** До продвижения длительных сессий: постоянный версионированный checkpoint/patch, идентичность источника, последняя подтверждённая запись и явная граница возможной потери последних действий. Запись снимка в фоне, согласованные метаданные. Восстанавливается локальная сессия, исходный мир автоматически не переписывается. Сначала можно сохранять конечный patch и контекст без полной старой Undo-истории; её отсутствие нужно явно обозначить. Публичный формат проекта и обмен патчами не являются обязательными зависимостями.

**D2. Локальная библиотека фрагментов.** После F2: файлы, имена, теги, anchor и ленивые миниатюры; размещение существующим Clipboard. Именованные выделения и пресеты полезны, если повторное использование подтверждается обычной работой.

**D3. Первая кисть Paint.** После R1/R3/R6 и минимального D1. Ненакопительная окраска выбранной области, существующие материал/условия, один мазок — один Undo. Геометрия по расстоянию вдоль траектории, ограниченная очередь; потеря поверхности разрывает мазок. Escape отменяет, отпускание вне окна и потеря фокуса завершаются по одному документированному правилу. Не соединять точки через пустоту и не обещать «видимую сторону» проверкой соседнего воздуха.

**Пакетная правка NBT** — сильный кандидат для сценария поиска и ремонта данных, но частота такого сценария неизвестна. Сначала одна замена существующего скалярного пути по зафиксированному набору результатов, сохранение типов, пропуски с причинами, один Undo. Не ограничивать действие текущей страницей поиска. Перенести выше кисти, если повторяющиеся NBT-правки являются реальной основной работой.

Пользовательскую сборку делать перед внешним распространением: одна явно поддержанная ОС, чистая установка, согласованные минимальные зависимости и полный маршрут открытия/сохранения. Наличие рабочего workspace не доказывает исправность опубликованных диапазонов зависимостей.

## Алгоритмические решения, которые стоит зафиксировать

### Область записи, чтения и неизвестные клетки

Пусть W — разрешённые клетки записи. Для соседской операции радиуса r область чтения R содержит W с окружающим слоем r. Записывается только W. Для нескольких последовательных фильтров суммарная область зависимости может быть шире одного r.

Неизвестная клетка не становится воздухом через `NOT`. Для простых условий достаточно сначала проверять покрытие данных, затем предикат. Сложную трёхзначную логику вводить, когда действительно нужны частично определённые выражения. Нынешний `Condition.matches(None)` сам по себе не доказывает ошибку: в некоторых путях None обозначает известную пустую клетку, а доступность проверяется отдельно.

Бюджеты: прочитанные клетки, проверенные кандидаты, изменённые клетки, байты NBT, временные массивы, очередь и время отмены. Маска с нулём совпадений всё равно может выполнить большую работу.

### Маски и морфология

Маска 16³ содержит 4096 бит = 512 байт полезных данных. Это не общий размер объекта Python и не стоимость плотного рабочего массива. Текущий Connected строит плотную int32-сетку всей загруженной области и ограничивает её 8 млн клеток; наличие секционного результата не делает вычисление разреженным. Сначала замер и ROI, затем решение о секционном алгоритме.

`Grow(S,r) = {p : d(p,S) ≤ r}`, `Shrink(S,r) = {p ∈ S : d(p,Sᶜ) > r}`. Метрика — часть операции: 6-соседей дают L1, 26-соседей — L∞, евклидово расстояние — L2. Не менять существующий Hollow L∞ скрыто под новым названием толщины.

Для первой прямоугольной рамки достаточно двумерной маски с квадратной окрестностью: `Dilate(S,r) \\ S` снаружи, `S \\ Erode(S,r)` внутри. Окно 5×7 и внешняя рамка ширины 1 дают 7×9 − 5×7 = 28 клеток на плоскости. Полное поле расстояний пока не требуется. Массив float64 256³ занимает 128 MiB; [SciPy EDT](https://docs.scipy.org/doc/scipy/reference/generated/scipy.ndimage.distance_transform_edt.html) возвращает именно float64, индексы ближайших клеток требуют дополнительной памяти.

### Воспроизводимый материал

Текущий hash(seed,x,y,z) сохраняет независимость от обхода; не переписывать его ради новой абстракции RNG. Сейчас `_change` передаёт локальные координаты, поэтому независимость от смены окна мира ещё не следует из детерминизма Mix. Ввести явный anchor и тест одинаковой мировой позиции после Refresh/resize, прежде чем сохранять пользовательские пресеты.

Веса задают вероятностные доли. При идеализированном независимом выборе доли p среди N клеток ожидаемое количество Np, стандартное отклонение √(Np(1−p)); фиксированный seed задаёт конкретный рисунок. Точные квоты требуют распределения по всей области и меняют свойства при расширении выделения. Сглаженный шум обычно не равномерно распределён, поэтому те же пороги не гарантируют прежние доли. Сначала пресеты и градиент; шум — после конкретного художественного запроса.

### Выдавливание и кисть

Для грани нужна пара `(cell, normal)`. Planar select использует 4-связность в одной плоскости; выдавливание добавляет `p + k·normal`, где k=1…depth. Источник читается из одной ревизии, конфликтующие назначения проверяются до применения. Перемещение стены без утолщения — отдельная операция.

Для Paint с радиусом r между точками A/B кандидат задаётся расстоянием от центра клетки до отрезка: `distance(center, segment(A,B)) ≤ r`. Это делает результат на одной траектории независимым от частоты событий, но не восстанавливает неизвестную кривую между редкими отсчётами. Повторно затронутая клетка хранит первое before и итоговое after один раз. Временный штрих имеет свой предел памяти.

### Сглаживание: полезная проверка, отложенная функция

Приложенный скрипт проверяет бинарную занятость одного синтетического куба, не материалы, NBT или реальные постройки.

| Проверка: куб 16³ в массиве 32³, σ=2, радиус 8 | Результат |
|---|---:|
| Исходное число клеток | 4096 |
| float32 blur, затем порог 0.5 | 3576, потеря 520 ≈ 12.7% |
| uint8 blur с тем же порогом | 0 |
| Top-K по сглаженной оценке | 4096 |
| Секции 16³ без halo против целого расчёта | 1336 отличающихся бинарных клеток |
| Halo 8 против целого расчёта | Максимальная ошибка 0 |

Дробный тип и радиус фильтра — явные параметры; SciPy хранит промежуточные массивы в выходном типе ([gaussian_filter](https://docs.scipy.org/doc/scipy/reference/generated/scipy.ndimage.gaussian_filter.html)). Для нескольких проходов нужны соответствующие дополнительные зависимости. Дополнение нулями на внешней границе тестового массива не является разрешением считать незагруженный мир воздухом.

Top-K решает ограниченную задачу: максимизировать сумму оценок выбранных клеток при их заданном числе K. Он не сохраняет связность, проходы, толщину, материалы или количество блоков каждого вида. Нужны допустимый домен C, защищённые клетки и условие 0≤K≤|C|. K считается для всей операции, не независимо по секциям. Полная сортировка O(|C| log |C|) в скрипте годится как эталон; частичное разбиение с детерминированным разрешением равенств — кандидат для реализации после профилирования.

Поэтому первым ландшафтным инструментом может стать ограниченный Flatten/Smooth выбранной поверхности. Нельзя определять грунт как верхний non-air: это может быть крыша, вода или листва. Объёмное сглаживание оставить экспериментом до явных требований к топологии и материалам.

## Порядок поставки и проверки

Начать с R1, R3 и первого исправления R2. Следом R4 и минимальная проверка R5. Протокол прерванного Save из R2 довести отдельно до выпуска записи миров. R6 строить поверх правильной базы сравнения R1. Затем F1/F2, F3 по потребностям, F4 как первый новый инструмент моделирования. D1 предшествует ставке на долгую работу и кисть; не требует полного формата проекта.

Для каждой поставки нужен законченный маршрут и только относящиеся к ней проверки. Основные инварианты:

- Apply показанного ChangeSet даёт показанный результат; устаревший ответ отклоняется.
- Undo возвращает семантическое содержимое, типы NBT, сущности и bounds; не сравнивать только число блоков.
- Невыбранные клетки clipboard не изменяют назначение, даже при Copy air.
- Unknown не разрешает запись и не влияет как воздух на соседские вычисления.
- Обработка целиком и с корректным halo совпадает; порядок обхода не меняет смесь.
- Save/Undo/повторный Save и отказ записи проверяются повторным чтением результата.

В `test_condition.py` обнаружена проверка `assert ... is False or True`, которая проходит при любом результате. Заменить её содержательным ожиданием в затрагивающем условия PR. Число зелёных тестов само по себе не доказывает контракт.

Для UX пройти: заменить только крышу со ступенями; вставить фрагмент с воздушной полостью и сундуком; повторить окно; работать со скрытым этажом; сохранить и открыть результат. Измерять завершение без помощи, ошибки области и время возврата после ошибки. Для производительности фиксировать файл, версии, окно и устройство; отдельно чтение, подготовку ChangeSet, IPC, геометрию, историю, Save и пик памяти GUI+worker. p50/p95 получать из повторов одной задачи, не из разных файлов. Тачпад и фокус проверять физически.

Первый результат этапа: корректные изменения относительно диска, исправленное восстановление файлов, ограниченная история и обычное завершение Save. Следующий видимый прирост: удобный материал, `.schem`-экспорт и выдавливание плоской грани с рамкой.
