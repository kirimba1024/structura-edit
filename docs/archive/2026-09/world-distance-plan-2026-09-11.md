# Дальность мира: текущий этап и следующий

Главный приоритет — скорость открытия, Refresh, Save и полёта. Полный список исправлений: [editor-feedback-plan-2026-09-11.md](editor-feedback-plan-2026-09-11.md). LOD ниже — план следующего этапа, не описание уже готовой функции.

После уточнения требований к обзору всех реальных чанков и качеству объёмных построек подготовлен [новый ресерч и план](world-overview-plan-2026-09-11.md). Он заменяет предложения ниже о будущем heightfield-обзоре и его обновлении; описание уже реализованных алгоритмов остаётся актуальным.

## Что принято сейчас

- Мир загружается по Open, F5 / Load here и Apply в World view distance. Полёт сам не читает новые чанки. Размещение за границей может загрузить необходимую область после явного Place / Preview changes.
- Обычный радиус 6: 13 × 13 колонн, 208 × 208 блоков. Радиус 3: 112 × 112; радиус 8: 272 × 272. Рост затрат примерно квадратичный по горизонтальному радиусу, дополнительно зависит от высоты и сложности моделей.
- Высота задаётся отдельно, по умолчанию ±32 блока от камеры с округлением до секций 16³. Это окно редактирования, а не весь мир по высоте.
- Для разработки запускать `--world-radius 1`. Настройки пользователя сохраняются отдельно; CLI не переписывает их.
- Текущие предохранители: радиус до 8, 8 млн ячеек, 2 млн загруженных блоков, 192 MiB геометрии. Это ограничения реализации, не обещание одинакового FPS для всех миров.
- Разные сущности интерфейса: Chunk columns — колонны 16 × 16 через загруженную высоту; Section grid — секции 16 × 16 × 16; пунктир — край загруженных данных.

## Уже применённые алгоритмы

1. Чтение palette/chunk: пакетное преобразование NumPy вместо создания отдельных NumPy-скаляров для каждого блока. Быстрая, но полноценная проверка обычных целочисленных координат.
2. Снимки: неизменяемые координаты и индексы разделяются, изменяемый NBT копируется. Никакого совместного изменения исходного документа.
3. Подготовка секций большого мира: один плотный int32-массив и выборка локального окна с ореолом соседей. Малые структуры используют простой разреженный путь.
4. Кэш мешей секций: LRU 96 MiB / 2048 записей, ключ включает содержимое и соседей, ресурсы, высоту и расположение. Неизменные акторы повторно используются. Изменение границы перестраивает необходимого соседа.
5. Установка сцены проходит порциями через Qt. Запросы отрисовки объединяются; простоящий редактор не рисует бесконечно.
6. Save применяет только патч к заново прочитанным чанкам. Интерфейсы Anvil переиспользуются по region-файлу; внешние изменения, конфликты, резервная копия и безопасная установка остаются частью записи.
7. Миникарта читает блоки, а не видимые 3D-грани. Срезы считаются отдельно; очередь содержит выполняющийся запрос и последнюю цель. Каталог материалов виртуальный, иконки ограничены видимыми строками и кэшем.

## Как измерять

Из корня workspace, на одной машине и одном мире, без параллельных тестов:

```bash
.venv-edit/bin/python libs/structura-edit/tests/benchmark_world.py /path/to/world --radius 6 --visible --output /private/tmp/world-r6.json
.venv-edit/bin/python libs/structura-edit/tests/benchmark_world.py /path/to/world --radius 8 --visible --output /private/tmp/world-r8.json
```

Сценарий сначала копирует мир во временный каталог. Измеряет Open, Refresh после открытия, повторный Refresh и Save одной правки; затем движение камеры. Личный мир не изменяется. Настоящий Qt event loop позволяет рабочим потокам выполняться; `QTest.qWait` не использовать для сравнения скорости Python-потоков.

Сохранять время до готовой сцены и карт, p95/max интервала GUI-таймера, RSS GUI + worker, число акторов, объём геометрии, завершённые кадры и время рендера. Сумма RSS может повторно учитывать общие страницы; это не физическая память процесса целиком и не пик. FPS скрытого окна не подменяет видимый прогон. Профилировать отдельно от итоговых замеров.

## Предлагаемая концепция дальней дальности

Две области с разным назначением:

- **Editable area** — точные блоки, NBT, сущности, выбор и редактирование. Яркая граница, как сейчас.
- **World overview** — дешёвая геометрия рельефа снаружи, только ориентир. Она не участвует в выборе блока, коллизиях, Save и Undo. При подлёте видно `Overview only · Load here`; F5 загружает точные данные вокруг камеры. До этого ничего не подгружается само.

Отдельная кнопка `Build overview…` задаёт центр, радиус и качество, показывает число колонн и оценку бюджета. Пользователь запускает одну ограниченную задачу с прогрессом и Cancel. Предыдущий обзор остаётся до успешной установки нового. Ключ результата проверяется перед установкой; отменённая или устаревшая задача не меняет сцену.

Первый прототип: радиус обзора 24, шаг 4 блока, фиксированные тайлы и одно-два кольца качества. Это кандидаты для замеров. 24 означает 2401 колонну против 169 у радиуса 6: первая загрузка всё равно требует чтения и декодирования. LOD уменьшает геометрию и память, но не делает холодный I/O бесплатным.

Хранить на ячейку высоту, цвет/материал поверхности и отдельный уровень воды, где он нужен. Не создавать тысячи полных блоков для дальнего обзора. Сначала использовать heightmaps чанка и читать необходимые верхние секции; при отсутствии или неподходящей карте высот — корректный проход сверху вниз. Не выдавать верх текущего ограниченного Y-окна за поверхность мира.

Такой heightfield не описывает пещеры, мосты и навесы. Для первого обзора это явное ограничение; точное редактирование остаётся в Editable area. Не внедрять сразу полноценный octree и произвольное упрощение всех моделей.

На границах тайлов нужны согласованные вершины и переходы между разрешениями; вода и растения не должны оставлять дырки. Внутри точной области обзор скрывается. Кольца можно выбирать по уже загруженным данным без I/O; создание новых данных — только кнопкой. Идея регулярных вложенных сеток и переходов описана в [GPU Gems: Geometry Clipmaps](https://developer.nvidia.com/gpugems/gpugems2/part-i-geometric-complexity/chapter-2-terrain-rendering-using-gpu-based-geometry); полный GPU-clipmap здесь пока не нужен.

## Память миникарты

Существующий SQLite-кэш проекций ограничен 48 MiB / 4096 тайлами. Он учитывает высотное окно, ресурсы и изменения файлов. Это ещё не полноценный атлас всей пройденной поверхности: нельзя склеивать верхние проекции разных Y-окон как одну достоверную карту.

Следующий шаг — один общий источник тайлов поверхности для World overview и памяти Top map. Идентичность: мир + измерение + координаты чанка + формат/ресурсы + версия исходных данных. Сохранять только посещённые/явно построенные тайлы, LRU и размер на диске. Отдельно показывать неизвестное, сохранённый обзор и точную текущую область. Неизвестное не превращать в воздух. Slices остаются точными срезами загруженных блоков; их не смешивать с архивной поверхностью.

Локальные несохранённые изменения перекрывают обзор; Save обновляет затронутые тайлы. Внешнее изменение region-файла инвалидирует зависимые записи; сначала допустима грубая инвалидизация файла, позже — точные версии чанков при наличии измеримой пользы.

## Порядок дальнейшей работы

1. Зафиксировать текущие замеры r6/r8. Разделить потери FPS на количество акторов, число граней, прозрачность и обновления карт.
2. При подтверждённой цене draw calls — объединять совместимую геометрию небольшими группами секций, сохранив локальное обновление. При цене граней — эксперимент с объединением соседних граней полных непрозрачных кубов. Не менять специальную геометрию, освещение, UV и прозрачность без тестов. См. [авторское описание greedy meshing](https://0fps.net/2012/06/30/meshing-in-a-minecraft-game/).
3. Реализовать и измерить общий тайл поверхности; память Top map без отдельной дублирующей базы.
4. Добавить явную Build overview и грубый рельеф, бюджеты, отмену, сохранение камеры, подпись Overview only.
5. Проверить стыки, воду, отрицательные координаты, смену измерения, устаревший кэш, локальные правки и полёт за край. Только после этого увеличивать стандартные радиусы.

Не включать стандартный автоматический `vtkLODActor` как готовое решение: он может заменять модель облаком точек или bounding box, что недостаточно для узнаваемого рельефа и детерминированного UX ([VTK API](https://vtk.org/doc/nightly/html/classvtkLODActor.html)). Автоподгрузка по полёту — отдельный будущий этап по запросу пользователя.
